## 二、缺陷清单

### B1【S1】小程序首页商品列表恒为空(「全部」页签无货)
- **现象**:微信小程序首页默认请求 `category_id=0`(index.js `query: { page:1, size:10, category_id:0, sort:'time' }` 全量透传),后端把 0 当作真实分类过滤 → 返回空。
- **证据**(库内 2 件在售商品时):
  - `GET /app/clothing/product/list?page=1&size=10&category_id=0` → `total:0`
  - `GET /app/clothing/product/list?page=1&size=10` → `total:2`
  - `GET /app/clothing/product/list?page=1&size=10&category_id=1` → `total:2`
- **对照**:pc-web `Home.vue` 有 `if (query.category_id) params.category_id=...` 保护(0 不传),故 PC 商城正常,仅小程序中招。
- **影响**:小程序首页/搜索后「全部」列表空白,只剩轮播与「热销」区有货;演示时第一屏就翻车。
- **修复建议**:小程序端 0 时不传该参数(与 PC 对齐);或后端 `category_id` 为 0 视为不限。二者取一。

### B2【S1】管理端「SKU/图片」可视化保存必败
- **现象**:商品管理 →「SKU/图片」→ 保存,接口必报「商品标题与价格必填」。sku-edit.vue 只提交 `{id, skus:[...], images:[...]}`,而后端 `product/update` 强制校验主字段 title/price。
- **证据**:按页面契约原样复刻请求
  `POST /admin/clothing/product/update {id, skus:[{skuName,price,stock,attrs}], images:[{url,sort}]}` → `code 1001 商品标题与价格必填`;补齐 title/price 后同请求成功(code 1000)。
- **影响**:演示「SKU 可视化键值对编辑」时保存必报错,功能入口不可用。
- **修复建议**:二选一 —— a) 页面保存时补带主字段(现有 row 里有 title/price);b) 后端把 skus/images 保存拆成独立方法(如 `product/saveSku`),不与主字段校验耦合。

### B3【S1】「订单发货」成功后无任何可见效果(空转)
- **现象**:管理端发货接口调用成功(code 1000,契约 `{orderId, logisticsCompany, logisticsNo}`),但:订单主状态不变(仍 paid,全程无 shipped 状态);管理端订单列表/详情无物流字段;买家侧无任何物流查询接口;买家仍可直接确认收货。
- **证据**:
  - `POST /admin/clothing/order/ship {orderId, logisticsCompany:'顺丰速运', logisticsNo:'SF123456BT'}` → success
  - 随后 `order/list` 该单 `status=paid`,`logistics` 字段仍是下单收货地址(consignee/phone/detail)
  - 存储层核实:物流数据实际写入了 `product_order_logistics`(company/no/shipped_at 齐全)→ 是「只写不读不展示」,不是没写
  - 用户 confirm 后 `shipped_at/received_at` 被同时打上时间戳(19:11:18 同一时刻)
- **影响**:演示「订单发货 + 物流」环节:管理端点了发货毫无反馈,买家也看不到任何物流信息;物流环节整体对用户不可见。
- **修复建议**(按演示闭环最小化):a) ship 成功后订单主状态推进为 shipped 并记录 shipped_at;b) 订单列表/详情(C 端 order/list、管理端 order/page、order/info)关联返回 logistics_company/logistics_no/shipped_at;C 端可提供订单物流查询;c) confirm(确认收货)前置校验状态 = shipped(与 B4 同修)。

### B4【S1】已支付即「已收货」:确认收货与评价均不校验发货/收货状态
- **现象**:状态机实际为 pending → paid → completed,confirm 对未发货订单直接放行;评价仅校验「订单归属 + 已支付」,未收货也能评价。
- **证据**:
  - 下单 → 支付 → `POST /app/clothing/order/confirm`(从未发货)→ code 1000,单直接 completed(多单复现)
  - paid 未确认订单 `POST /app/clothing/product/review {orderId,productId,rating,content}` → code 1000 成功
- **影响**:业务语义错误(「已发货→待收货→确认收货→完成」链条缺失),配合 B3 让物流/发货环节形同虚设;未收货即可评价,评价公信力受损。
- **修复建议**:confirm 校验订单状态=shipped;review 校验订单状态=completed(收货后)。

### B5【撤回-黑盒误报】退款同意后库存不回补
- **结论**:读码复核(refund service approve)实为**回补库存并回退销量**(按 items 数量 SQL 自增+下限保护);黑盒"缺口"是测试脚本漏算了另一笔 pending 未付订单占用的库存。
- **复验**:回归测试下单扣 1 → 退款 approve → 库存 29→30 正确回补。此条非缺陷,无需修改。

### B6【撤回-有意设计】已收货(completed)订单仍可申请退款
- **结论**:refund service 注释明确「当前实现为仅支持全额退款(approve 即视为退款完成,无退货寄回分支)」,apply 允许 paid/completed 为有意设计(收货后仅退款)。此条非缺陷,维持现状即可。

### B7【S2】数据库原生报错信息直接透传给客户端
- **现象**:参数类型非法时,把 MySQL 底层错误原文返回给用户。
- **证据**:
  - `GET /app/clothing/product/detail?id=abc` → `code 1001, message: Unknown column 'NaN' in 'where clause'`
  - `POST /app/clothing/cart/update {id:{...对象},quantity:1}` → `code 1001, message: Truncated incorrect DOUBLE value: '[object Object]'`
- **影响**:泄露 SQL 实现细节(SQL 注入探测的顺风车);用户看到英文底层报错,观感差;说明服务端缺参数类型/白名单校验。
- **修复建议**:入口参数做类型与范围校验,非法值返回友好业务错误;禁止把 ORM 异常 message 直出。

### B8【S3】加购数量为 0 时接口成功并插入 0 件购物车行
- **证据**:`cart/add {skuId, quantity:0}` → code 1000,购物车列表新增一条 quantity=0 的行;而 quantity=-3 会被拒(「参数错误」)。校验对 0 与负数不一致。
- **影响**:购物车出现「0 件」垃圾行;前端虽有 qty<=0 兜底,接口仍应拒绝。
- **修复建议**:quantity <= 0 统一拒绝。

### B9【S3】商品列表分页参数无边界
- **证据**:`size=0 / size=99999 / page=-1 / page=abc / size=xyz` 全部静默 code 1000,不报错(各自返回不同空/全量结果),`size` 无上限有全表拉取风险。
- **修复建议**:page>=1、size 封顶(如 100),非法值拒绝或回落默认值。

### B10【S3】排序字段无白名单
- **证据**:`sort=xxx` 静默 code 1000(当作默认排序处理,不报错也不拒绝)。
- **修复建议**:`sort` 白名单(time/sales 等),未知值报错或忽略并记录。

### 观察项与数据卫生(非缺陷)
- 演示账号历史存在 **2 条 pending 退款记录 reason 为乱码**(order_refunds id 1/2,疑似录入工具编码问题),建议演示前人工修正或清理。
- 商品/评价等错误文案偶带波浪号「登录失效~ / 账户或密码不正确~」,风格不一致(纯观感)。
- 未登录访问需鉴权接口统一返回业务码+「登录失效~」(HTTP 200 + code 1001),行为一致可接受;管理端鉴权失败返回 HTTP 401 + JSON,正常。
- 登录失败提示不区分「手机号不存在/密码错误」(防枚举),符合安全预期。
